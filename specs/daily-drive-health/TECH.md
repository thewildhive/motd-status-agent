# Daily Drive Health: Technical Design

## Context

[PRODUCT.md](PRODUCT.md) defines the contract. The [agent service](https://github.com/thewildhive/motd-status-agent/blob/v0.3.1/cmd/motd-status-agent/main.go#L70) runs as the workload user and refuses root. Leave its deployment, permissions, and `/v1/status` unchanged. In `go-motd`, extend [system configuration](https://github.com/thewildhive/go-motd/blob/278f9308158ae8cbc82b3155079753252360510c/config/config.go#L25), [report assembly](https://github.com/thewildhive/go-motd/blob/278f9308158ae8cbc82b3155079753252360510c/report.go#L83), and the existing terminal system display. Both sides remain standard-library Go; `smartctl` is a host prerequisite for the collector only.

## Collector and Deployment

- Ship a separate `motd-drive-health` command and opt-in systemd service and timer in the agent repository. Do not enable them through the existing agent installer. Document an administrator-controlled, one-shot root service: no listener, no network access, no shared credentials or device permissions with the agent. Use `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, and a systemd-managed `StateDirectory=motd-drive-health`; allow the actual device access `smartctl` needs rather than using `PrivateDevices=yes`.
- Run daily in host local time with `Persistent=true`. Immediate collection uses `systemctl start motd-drive-health.service`; systemd coalesces starts while the oneshot is active. Use the unit as the only supported collection entry point. Do not enable it for drives that another monitor already polls. No smartd adapter or alerting is included.
- Read a root-owned `/etc/motd-drive-health/config.json` with an explicit list of stable `/dev/disk/by-id/` whole-drive identifiers, unique short printable labels, and device kind (`ata` or `nvme`). Reject malformed configuration, partition selectors, and duplicate resolved devices. Resolve identifiers on each run; verify the returned device identity against the stable identifier as part of enrollment and collection. For NVMe, monitor one namespace identifier per physical controller and reject duplicate controllers. Missing, mismatched, or unsupported devices produce unknown, never a fallback to a numbered device node. Hardware RAID and bridge-specific passthrough are out of scope.
- Inventory entries use `{id, label, kind}`. `id` is a basename under `/dev/disk/by-id/`: `ata-MODEL_SERIAL`, `nvme-MODEL_SERIAL_NSID`, `nvme-eui.HEX`, or `nvme-nguid.HEX`. Labels are 1–32 printable ASCII characters without leading or trailing spaces; the snapshot uses the same label rule.
- Run `smartctl` directly from an administrator-controlled absolute path, never through a shell. Read identity, overall health, and attributes in one JSON invocation (`-j -i -H -A`). For ATA, require the non-waking standby check (`-n standby`) in that same invocation; a low-power skip or inability to establish that check yields unknown, with no follow-up identity probe. Collect serially, cap inventory at 32 drives and each invocation at 10 seconds and 256 KiB of output, and set a service deadline above the worst-case serial budget. Log normalized failure reasons without raw telemetry. An invalid configuration or failed publication exits nonzero and does not refresh the old snapshot.
- Pass the configured native protocol (`-d ata` or `-d nvme`) explicitly. Device-type autodetection can wake an ATA drive before the standby check. Require a smartctl version supporting `-n standby,STATUS,STATUS2` and configure distinct low-power and unsupported-check outcomes; do not retry with autodetection or bridge probing.
- Decode the smartctl exit status as a bitmask, not a Boolean. A valid explicit failure takes precedence over a warning. For ATA, use overall health and current prefail flags, not historical error or self-test log flags. For NVMe, require the critical-warning byte: reliability degraded, media read-only, or spare below threshold are failed; other recognized current warning bits are warning. Unknown bits without a recognized failure or warning, missing required fields, invocation failures, and incomplete reads that do not establish an explicit failure yield unknown. Use stable reason codes, not tool output.

## Snapshot and Consumer

- Publish `/var/lib/motd-drive-health/status.json` as a root-owned regular file, mode `0644`, in a root-owned non-writable-to-others directory. Write a temporary file in the same directory and rename over the previous file after a complete run, including partial device failures. Preserve the last complete file if interrupted. The schema is `schema_version: 1`, `observed_at` (UTC RFC 3339 completion time), and `drives` (nonempty array of `{label, state, reason}` sorted by label). No device identifiers or raw logs cross the boundary. A successful collection of all unknown rows is still a fresh snapshot, not healthy.
- This repository owns device probing, classification, scheduling, and snapshot publication. `go-motd` owns snapshot consumption and all user-facing terminal and JSON display; it does not invoke `smartctl`.
- The v1 state/reason pairs are exhaustive: `healthy`: `passed`; `failed`: `overall_failed` or `nvme_critical`; `warning`: `ata_prefail_now` (a prefail attribute currently at or below threshold, not merely marked prefail) or `nvme_advisory`; `unknown`: `missing`, `identity_mismatch`, `access_denied`, `sleeping`, `unsupported`, `timeout`, `invalid_response`, or `probe_error`. Use `probe_error` when the cause cannot be distinguished. Do not emit a health finding without a verified identity. Reject a snapshot containing any other pair.
- Add opt-in `system.drive_health: true` in `go-motd` with a fixed local path. Open without following symlinks; reject nonregular files, files not owned by root, files writable by group or others, and files over 64 KiB. Validate schema version, timestamps, unique labels, and state/reason values. Reject timestamps more than five minutes in the future; older than 36 hours is stale. Use timestamps inside the file, not mtime. Missing or rejected data is unavailable with debug diagnostics. Do not include stale drive counts as current results.
- Open with `O_NOFOLLOW | O_NONBLOCK` so a FIFO cannot stall login before validation. Check type, owner, permissions, and size on the opened descriptor, then read at most 65,537 bytes from that descriptor. Reject reads over 65,536 bytes even if the file was smaller at open time.
- Follow the [go-motd display spec](https://github.com/thewildhive/go-motd/blob/main/specs/daily-drive-health/PRODUCT.md) for the compact `Drives` row: `healthy`, `degraded: <affected drives>`, `stale`, or `unavailable`. Emit top-level `drive_health` only when enabled, with `status` (`fresh`, `stale`, `unavailable`), `observed_at` when known, and per-drive rows only when fresh. Use the same report for terminal and JSON. Neither reader nor login runs any probe or needs membership in a disk access group.

## Verification

- On an approved disposable Linux host, enroll representative ATA and NVMe devices, run the systemd service, and record the journal, root-owned snapshot, and unprivileged `go-motd` terminal and JSON output. Confirm the timer persists across a missed run and that overlapping starts do not run parallel collectors (Behavior 1-4, 6, 8).
- Use a known sleeping ATA drive and an intentionally absent stable identifier on that host. Confirm unknown reasons and that an unrelated healthy drive remains visible. Inspect captured vendor telemetry for warning/failure mapping without inducing a disk fault (Behavior 3-5).
- In the disposable environment, exercise the real consumer with stale, missing, rejected, and restored snapshots. Confirm that the terminal, JSON and debug outputs agree, that no collection is triggered by the login path, and that the container section is unchanged (Behavior 6-8). Do not add or run test suites.
- Include a FIFO with no writer among the rejected snapshots: login must complete without waiting. Check rejection of an oversized file and of a recognized reason paired with the wrong state.

## Delivery

Agree on the snapshot contract before splitting implementation. The collector and systemd packaging can then land in a protected PR on `motd-status-agent`; the config, reader, and display can land independently in a protected PR on `go-motd`. Verify both together on a disposable host before enabling the timer on an installed machine.
